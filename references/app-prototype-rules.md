# APP/H5 移动端原型设计规则

本文件用于 APP、H5、小程序和移动端需求原型。规则提炼自参考移动端 HTML 的手机外壳、固定区/滚动区、卡片、选择、底部操作、成功页、Toast、状态预览和文案编辑机制，但不绑定任何品牌、国家、业务对象、地图服务或具体数据。

## 既有设计优先

每次新建或迭代前，先执行 [SKILL.md 的“Figma 设计检索与高保真复用”](../SKILL.md#figma-设计检索与高保真复用默认执行)。对实际匹配的业务界面，优先复用已读取的 Figma 页面组件、视觉参数和交互流程；下文中的颜色、字号、间距、卡片和按钮等默认值用于补足没有对应参考的部分，不覆盖已选设计。外层评审布局、手机适配、独立滚动、离线交付和需求说明规范继续适用。用户最新要求优先于设计参考。

## 1. 页面整体展示布局

所有 APP/H5 原型最终交付页面采用：

```text
页面整体
├── 左侧原型展示区：约 65%
└── 右侧需求说明区：约 35%
```

- 始终保持左右结构，不自动切换为上下结构。
- 页面定位为桌面端需求评审展示页，最小宽度建议 1280px。
- 小屏幕可出现页面整体横向滚动，不隐藏任一侧内容。
- 左右区域间距保持 16px 至 24px，高度一致并分别滚动。
- 页面背景使用浅灰或浅蓝灰中性背景。
- 原型和需求说明直接放在蓝灰色展示画布上，外层不使用整块白色卡片容器；右侧说明内部模块可以使用白底小卡片。
- 右侧说明不得被手机内部弹层、遮罩或成功页覆盖。

## APP/H5 原型展示外层规范

- APP/H5 评审页使用蓝灰色或浅蓝灰色画布背景。
- 左侧手机原型直接展示在画布上，不使用整块大白底容器包住手机。
- 右侧需求说明直接展示在画布上，不使用整块大白底容器包住整列说明。
- 右侧说明内部的小模块允许使用白底卡片，以承载字段、规则、状态和验收信息。
- 小卡片可以保留轻圆角、细边框和极淡阴影，但不得重新形成“大白板套内容”或“卡片套卡片”的视觉效果。
- 整体追求展示画布感，风格轻量、通透、专业、克制；允许使用透明分区、淡描边或弱阴影。
- 左侧约 65%、右侧约 35% 的外层比例保持不变，左右区域仍需独立滚动。
- 始终保持左右布局，小屏幕只允许页面整体横向滚动，不自动切换为上下结构。
- 本节仅适用于 APP/H5 移动端评审展示，不应用到 Web 后台模板或 Web 后台规则。

## APP/H5 固定评审画布与说明滚动规则

- 评审页外层使用固定视口高度，建议 `height: 100vh`；禁止右侧说明内容把整个网页向下撑高。
- 工作区和左右面板必须设置 `min-height: 0`、`overflow: hidden`，保证左侧手机展示区和右侧说明区始终等高。
- 左侧手机外壳完整限制在左侧展示区内；手机内部列表、表单或结果内容继续在手机屏幕内部独立滚动。
- 右侧需求说明拆分为固定标题区和可滚动正文区：标题区不参与正文滚动，正文区使用 `flex: 1`、`min-height: 0` 和 `overflow-y: auto`。
- 右侧滚动只作用于需求说明卡片区域，不允许触发整个 body 的纵向滚动，也不允许滚动覆盖左侧手机。
- 页面切换或状态切换时，只更新说明正文和标题文案，不改变固定高度、左右比例和滚动边界。

## 2. APP 原型在左侧的呈现方式

- 手机设备在左侧原型区居中展示，手机周围保留合理留白。
- 手机外壳尺寸接近真实移动设备比例，不因左侧区域较宽而横向拉伸。
- 默认在一个左侧区域展示一个主手机，多页面通过交互切换。
- 只有用户明确要求页面总览时，才并排展示多台手机。
- 建议手机基准尺寸：外壳宽度 390px 至 410px、高度 810px 至 850px。
- 建议外壳圆角 42px 至 48px、屏幕圆角 32px 至 38px，使用深色边框和轻微阴影。
- 原型内部按移动端尺寸设计，不把 Web 后台直接缩小成手机页面。

### 手机外壳视口适配

- 手机基准尺寸用于保持移动端比例，不代表必须以原始尺寸撑满评审页。
- 左侧展示区应根据当前 Web 页面可用高度计算缩放比例；可用高度不足时，使用 `transform: scale(...)` 或等价方式等比缩小手机外壳。
- 缩放必须同时作用于手机外壳和内部屏幕，保持宽高比例、圆角、阴影和点击区域一致，不得拉伸或裁切手机外框。
- 手机完整外框应在常见桌面浏览器视口内直接可见，不得因固定手机高度造成页面纵向外层滚动。
- 手机内部较长的业务内容仍使用屏幕内独立滚动；外层适配不能取消表单、列表和成功页的业务滚动能力。
- 浏览器窗口尺寸变化时重新计算缩放比例，并保持手机在左侧展示区居中；右侧说明区不受缩放层影响。
- 左侧展示区若已通过缩放完整容纳手机，可关闭左侧外层滚动；右侧需求说明仍需保持独立滚动。

## 3. 手机外壳规范

参考 HTML 的 `.phone` 和 `.screen` 结构，手机外壳至少包含：

- 深色设备边框。
- 圆角屏幕和 `overflow:hidden` 内容裁切。
- 内部页面层级和独立屏幕滚动区域。
- 状态栏、移动端页面和底部操作栏的清晰层级。

可以根据需求增加刘海、灵动岛或 Home Indicator；没有明确依据时不要堆叠复杂硬件细节。

## 4. 状态栏规范

参考 `.statusbar`：

- 默认包含时间、网络信号、Wi-Fi 和电池。
- 高度约 32px 至 36px，左右对齐。
- 图标优先使用内联 SVG 或 CSS 图形，不依赖外部图标库。
- 状态栏只用于视觉模拟，不参与业务操作，不随业务列表滚动。
- 微信 H5、浏览器 H5 或小程序可按真实场景调整顶部结构。

## 5. 移动端顶部导航栏

参考 `.m-header`：

- 默认包含返回按钮、居中页面标题和右侧品牌/操作/占位区域。
- 高度约 44px 至 52px，返回区域点击范围不小于 32px。
- 标题过长时省略或合理换行，不挤压返回和右侧区域。
- 顶部导航固定，不随主内容滚动。
- 返回按钮必须有明确结果和交互反馈；无返回目标时应隐藏或禁用并在说明中标注。

## 6. 移动端页面滚动结构

优先使用以下结构：

```text
.statusbar  固定
.m-header   固定
.m-fixed    关键摘要/筛选，可固定或吸顶
.m-list     主内容独立滚动
.m-footer   底部操作固定
```

- 页面内部滚动，不能让整个手机外壳随页面一起滚动。
- 固定区域和滚动区域边界明确；滚动区使用 `-webkit-overflow-scrolling: touch`。
- 底部按钮不能遮挡最后一条内容，滚动区底部要预留操作栏和安全区高度。
- 可以隐藏视觉滚动条，但必须保持可滚动。
- 外层页面不得因为手机基准高度产生纵向滚动；需要缩放时，优先缩放外壳整体，不能只压缩某一段业务内容。

## 7. 移动端卡片规范

适用于业务对象、用户、地址、服务、结果和配置内容：

- 白色卡片，圆角约 10px 至 14px，内边距约 12px 至 16px。
- 卡片之间保持统一间距，使用轻微边框或阴影，不做过度立体效果。
- 主标题、辅助信息、标签和操作层级清晰。
- 避免把所有信息堆进一张巨大卡片，应按任务拆分信息块。

## 8. 选择组件规范

参考 `.seg` 和 `.seg-item`，适用于方式、类型、服务、时间和单选卡片：

- 选项具有明显点击区域和足够触摸面积。
- 选中态使用品牌色边框、浅色背景和勾选标识，不只靠文字颜色。
- 每个选项包含标题和简短说明；未选中态保持中性。
- 点击后立即更新后续页面内容、摘要或底部按钮状态。
- 单选和多选语义必须明确，不得用相同视觉混淆。

## 9. 列表卡片规范

参考 `.pudo` 的信息卡片结构，但统一改为通用业务对象：

- 列表项可包含主标题、次要信息、地址/说明、时间/状态、距离/附加数据和次级操作。
- 整个卡片可点击时要有选中或按压反馈；卡片内次级操作必须阻止冒泡。
- 内容过长时正常换行或截断，不破坏手机宽度。
- 移动端使用列表卡片，不使用 Web 宽表格代替。
- 空列表和搜索无结果必须有清晰文案及下一步操作。

## 10. 提示信息规范

参考 `.notice`：

- 普通提示使用品牌浅色背景。
- 警告使用橙色浅背景，错误使用红色浅背景。
- 文案简洁，重点时间、限制或风险可加粗。
- 不用大段连续说明替代结构化提示。

## 11. 搜索和定位规范

- 移动端搜索框高度约 38px 至 44px，圆角约 8px 至 12px，包含搜索图标和占位文字。
- 输入后可过滤列表，清空后恢复完整列表；搜索无结果进入明确空态。
- 定位区域展示当前定位状态，并提供重新定位。
- 定位权限拒绝或定位失败时说明原因并提供手动选择等替代方案。
- 原型无法真实定位时可以使用模拟状态，但必须在右侧说明和待确认事项中标注。

## 12. 底部操作栏规范

参考 `.m-footer` 和 `.btn-cta`：

- 固定在手机屏幕底部，使用白色背景、顶部细边框或轻阴影。
- 可以包含左侧摘要和右侧主按钮，也可以使用单个通栏主按钮。
- 主按钮高度约 42px 至 48px，禁用时不可响应提交。
- 未满足选择、填写或校验条件时显示禁用态；满足条件后立即启用。
- 点击后显示加载中，防止重复提交，并根据结果进入成功或失败状态。
- 滚动内容底部必须预留操作栏高度和 iPhone 安全区。

## 13. 成功页规范

参考 `.m-success`：

- 至少包含成功图标、成功标题、成功说明、核心结果信息和下一步操作。
- 成功页限制在手机屏幕内，可覆盖当前业务页面但不能覆盖右侧需求说明。
- 成功页内部可独立滚动，关键结果要突出。
- 关键业务成功不能只用 Toast 表示；完成按钮应返回合理页面或结束流程。

## 14. Toast 规范

参考 `.toast`：

- Toast 限制在手机屏幕内，默认显示约 1.5 秒至 2 秒。
- 文案简短，不遮挡关键按钮。
- 用于轻量反馈；关键失败必须使用页面提示、弹层或明确错误状态，不能只依赖 Toast。

## 15. 页面状态预览规范

每个 APP 原型按实际业务提供可切换的关键状态，例如初始、已选择、加载、空、异常、成功和禁用状态：

- 状态预览工具用于需求评审，不属于真实业务页面。
- 预览按钮可切换页面或状态，标明当前状态，不阻断正式业务交互。
- 导出 HTML 后状态预览仍可使用，刷新后有明确默认状态。

## 16. 文案编辑与导出规范

参考 HTML 的编辑机制并保持与 Web 模板一致：

- 可编辑文案使用 `[data-k]` 和 `contenteditable`。
- 文案通过 `localStorage` 保存，同一 key 的文案同步更新。
- 支持恢复默认、导出单文件 HTML；导出时写入已编辑文案。
- 头像、图标、装饰元素不需要支持文案编辑。
- 导出文件必须仍能双击打开，不能依赖服务端。

## 17. 真实移动端交互规范

至少实现与需求相关的基础交互：返回、选项切换、列表选择、搜索、表单输入、底部按钮启用/禁用、提交确认、成功页、Toast、弹窗、页面切换、空态和异常态。不允许只制作静态截图式页面。

## 18. 移动端异常状态规范

按业务需要覆盖网络失败、加载失败、定位失败、权限拒绝、列表为空、搜索无结果、提交失败、重复提交、数据失效、页面超时和服务不可用。不是每个页面都必须展示全部异常，但分析和说明要覆盖相关异常。

## 19. 安全区规范

- 顶部状态栏、底部操作栏和 iPhone Home Indicator 应有清晰安全边距。
- 内容不能紧贴屏幕边缘，底部按钮不能被 Home Indicator 遮挡。
- 使用 `padding-bottom`、`env(safe-area-inset-bottom)` 或等价方案处理底部安全区。

## 20. 视觉原则

- 简洁、专业，使用统一品牌色，信息层级清晰，主要操作突出。
- 字号不能过小，触摸区域足够大；不使用 Web 后台式密集布局。
- 不在移动端堆叠过多信息，不滥用渐变、阴影和复杂硬件装饰。
- 不擅自增加没有业务依据的功能。

## 21. 右侧 APP 需求说明卡片

右侧需求说明必须与当前 APP 页面或状态同步，并至少包含：页面名称、页面目标、目标用户、页面入口、前置条件、页面结构、展示字段、可操作内容、默认状态、交互规则、按钮规则、校验规则、页面跳转、成功反馈、失败反馈、加载状态、空状态、权限或系统能力、数据来源和验收标准。

- 说明外层直接放在展示画布上；内部模块使用白色小卡片，保留 12px 至 16px 圆角、轻微边框或极淡阴影。
- 内容区独立滚动，标题区可吸顶但不遮挡正文和编辑工具。
- 模块清晰分组，密集段落拆成短条目、标签或提示卡片。
- 重点业务规则可用浅色提示框突出，流程使用编号结构。
- 说明中不得出现左侧原型没有依据的字段、按钮或状态。

## 22. APP 按钮说明规则

每个重要按钮必须说明：按钮名称、显示条件、默认状态、启用条件、禁用条件、点击后的前端处理、是否调用接口、加载中状态、成功后的结果、失败后的结果、是否允许重复点击、是否需要二次确认和页面跳转结果。

## 23. APP 页面流程规则

生成 APP 原型前，必须先形成页面流程，例如：

```text
入口页面 → 信息确认 → 方式选择 → 内容选择或填写 → 确认提交 → 提交处理中 → 成功页 → 完成或返回
```

同时识别异常分支：定位失败应提示原因并允许重新定位或手动选择；提交失败应保留已填写内容、显示失败原因并允许重试；数据失效应提示刷新并返回上一步或重新加载。

## 24. 参考 HTML 通用化边界

参考 HTML 中的 `.phone`、`.screen`、`.statusbar`、`.app`、`.m-header`、`.m-fixed`、`.m-list`、卡片、选择组件、`.m-footer`、`.btn-cta`、`.m-success`、`.toast`、`.editbar`、`[data-k]`、`localStorage`、`exportHTML()`、`resetCopy()` 和 `gotoState()` 可作为实现骨架。

沉淀时必须去除参考案例中的品牌名称、国家/城市、具体业务流程、具体字段、地图服务、接口名称、运单号和固定数据，不得将其当成所有 APP 原型的默认内容。
