# 原型设计规则

## 0. Web 设计规范引用规则

默认情况下，Web、PC、后台或管理端原型只按本文件规则和 `templates/prototype-template.html` 生成，不需要任何外部文件。

如果 `SKILL.md` 的“可选配置”里填写了 `web_design_references`（本地 Axure `.rplib`、截图、PDF 或设计说明），生成前先参考这些文件。参考重点包括页面模板、后台信息架构、导航层级、常用布局、基础组件、字号、颜色、间距、表格、表单、弹窗、状态和反馈表达。执行时遵循以下优先级：

1. 用户明确的业务需求和交互要求。
2. 配置的设计规范中的通用视觉与组件模式。
3. 本文件中的 Web 原型规则。
4. `templates/prototype-template.html` 的可复用实现结构。

配置的设计规范文件是外部只读参考，不直接嵌入最终 HTML。只复用通用视觉和交互模式，不复制其中没有业务依据的页面名称、示例字段、示例数据或业务流程；若规范与用户需求冲突，以用户需求为准。当前环境无法解析这些文件时，应明确说明并请求截图、PDF或可读导出，不得将未读取的内容当作已确认规范。

本节仅适用于 Web 后台原型，不应用到 APP/H5 模板和移动端页面。

## 1. Web 后台布局规则

- 默认使用左右布局：左侧约 65% 为原型，右侧约 35% 为需求说明。
- 原型区和说明区分别滚动，避免一个区域滚动带动另一个区域。
- 原型区包含顶部栏、侧边栏和内容区，保持后台系统的空间层级。
- 内容区使用卡片、工具栏、表格和表单分组，控制信息密度。
- 避免固定宽度导致横向溢出；表格允许单元格换行。
- 页面切换时同步更新说明标题、页面目标和详细规则。

## 2. 列表页规则

- 提供与业务字段对应的筛选条件、查询和重置。
- 表格字段与需求说明一一对应，列顺序保持一致。
- 状态使用颜色和文字双重表达，不只依赖颜色。
- 分页按钮应反映当前页、总页数和可用状态。
- 操作列只放有业务依据的操作；每个操作都要有成功和失败反馈。
- 空结果时展示空状态、清晰文案和可执行的下一步。

## 3. 新增/编辑页规则

- 表单按业务顺序分组，必填项有明确标识。
- 编辑页回显原数据，保存时区分新增和更新。
- 保存前执行必填、格式、范围和重复校验。
- 保存失败保留用户已填写内容，并在字段附近或页面顶部给出原因。
- 保存成功给出明确提示并按需求返回列表或留在当前页。
- 取消和返回不能静默丢失重要输入；必要时增加确认提示。

## 4. 弹窗和抽屉规则

- 弹窗用于确认、轻量查看或少量补充操作；抽屉用于较完整的详情或编辑。
- 标题说明目的，主按钮说明结果，关闭按钮可用且行为明确。
- 弹窗打开后焦点和关闭路径清晰，背景层不应遮挡重要反馈。
- 删除、停用或覆盖等高风险操作必须说明影响并提供取消。

## 5. 状态展示规则

- 统一使用业务状态名称，例如“启用”“停用”，不要只写英文或颜色。
- 为每个状态列出可进入状态、允许的操作和操作后的反馈。
- 状态要形成闭环：用户能看到当前状态，也能通过明确操作进入下一状态。
- 不展示原型没有实现的状态；不把接口成功假装成真实持久化。

## 6. 多选数据展示规则

- 一个配置关联多个对象时，默认在同一条记录内合并展示。
- 使用标签、换行或“更多”展开，不拆成多条记录。
- 展示内容应包含用户识别所需的编码和名称，并使用明确分隔符。
- 过滤条件要说明匹配一条关联对象还是整条配置记录。

## 7. 按钮反馈规则

每个重要按钮至少覆盖：

| 阶段 | 必须说明 |
| --- | --- |
| 显示 | 当前角色和状态下是否展示 |
| 点击 | 什么条件下可点击，是否需要确认 |
| 处理 | 页面如何校验和改变数据 |
| 成功 | 提示、跳转、刷新和状态变化 |
| 失败 | 错误原因、保留输入和重试方式 |

## 8. 空状态和异常状态规则

- 无数据：说明当前筛选没有结果，提供重置或新增入口。
- 加载失败：说明失败，保留筛选条件，提供重试。
- 保存失败：保留表单内容，标注原因，不返回列表。
- 重复数据：指出冲突对象和冲突规则，不清空用户输入。
- 无权限：隐藏不允许的操作，并在必要时显示只读说明。

## 9. 原型与需求说明同步规则

- 每个可见字段、按钮和状态都必须在右侧说明中出现。
- 说明中列出的重要字段、按钮和状态必须在原型中有对应实现或明确标记未实现。
- 页面切换采用同一页面标识驱动原型视图和说明内容。
- 每次修改字段、状态或交互后，同时更新模板中的数据、文案、校验和验收标准。
- 交付前按 `references/self-checklist.md` 做一次逐项核对。

## 10. 左右评审布局规则

适用于需要同时展示可交互原型和页面需求说明的桌面端评审场景：

- 使用固定左右结构，左侧为交互原型，右侧为需求说明，不切换为上下结构。
- 评审页面外层使用 `html, body { height: 100%; }` 和 `height: 100vh`，禁止需求说明内容把整个网页向下撑高；外层页面默认隐藏纵向滚动。
- 左右面板必须使用 `min-height: 0`，工作区使用 `overflow: hidden`，确保左右区域始终等高并被限制在浏览器视口内。
- 左侧约占 65%，右侧约占 35%；右侧最小宽度建议不低于 360px，保证说明文字可读。
- 页面整体建议设置最小宽度 1280px。宽度不足时允许页面整体横向滚动，不隐藏任一侧内容，也不极端压缩字号和控件。
- 页面背景使用浅灰或浅蓝灰；内容区域居中，四周保留合理留白；左右间距保持 16px 至 24px。
- 原型区和需求说明区保持高度一致，并分别设置滚动容器：左侧由内容区或表格容器独立滚动，右侧仅由需求说明正文容器独立滚动。
- 右侧需求说明标题区使用固定高度的非滚动区域，需求说明卡片正文使用 `flex: 1`、`min-height: 0` 和 `overflow-y: auto`；标题在滚动卡片时始终可见。
- 左侧顶部导航、侧边导航和页面内容应明确分层：顶部导航不随内容滚动，页面内容在左侧内部滚动；不得让 body 或整个评审页面承担业务内容滚动。
- 不使用 CSS `order` 作为唯一的左右交换手段。优先通过清晰的 DOM 结构表达：工作区包含原型面板和需求说明面板，原型面板在前，说明面板在后。
- 左侧原型面板和右侧说明面板应有独立的白色卡片容器、圆角、轻微边框或阴影；避免两个区域视觉黏连。
- 页面切换时，原型页面、需求说明标题和需求说明正文使用同一页面标识同步更新。
- 不允许原型内容覆盖右侧说明，不允许说明面板覆盖原型；抽屉、弹层和图片查看器只能限制在左侧原型容器内。
- 表格宽度不足时，只允许在左侧原型内部横向滚动，不得导致整个评审页面横向错位。
- 响应式规则不得把页面改成上下结构；小屏场景只通过页面整体横向滚动保持桌面端评审布局。

推荐结构：

```html
<div class="prototype-workspace">
  <section class="prototype-panel">
    <!-- 浏览器外框和交互原型 -->
  </section>
  <aside class="requirement-panel">
    <!-- 需求说明卡片 -->
  </aside>
</div>
```

## 11. 需求说明卡片规则

右侧需求说明不是原型旁边的一段长文案，应设计为可快速扫描的独立卡片面板：

- 使用白色背景、12px 至 16px 圆角、轻微边框或阴影，和页面背景形成层次。
- 顶部信息区可吸顶，但不能遮挡页面标题、编辑工具或正文；编辑工具展开时应进入正常文档流。
- 内容区独立滚动；滚动时保留页面名称或当前模块标题，使评审者不易迷失上下文。
- 信息按模块分组，至少覆盖：系统信息、页面名称、页面目标、本次原型范围、查询条件、列表内容、核心交互、状态流程、计算规则和原型限制。
- 将密集长段落拆成短条目、短句、标签或小卡片；每个模块只表达一类信息。
- 模块标题使用清晰层级，正文保持可读字号和足够行高；避免整面板使用过小的灰色文字。
- 模块之间使用 12px 至 20px 间距或分割线，保证信息分组明确。
- 重点业务规则可使用浅蓝色提示卡片突出，但避免大量高饱和色、无意义图标或过度装饰。
- 状态流程优先使用纵向编号节点、状态名称、说明文字和简单连接线，不使用复杂流程图。
- 当前页面的字段、按钮、状态、计算规则和异常说明必须与左侧原型对应；不在右侧说明中加入原型没有依据的功能。
- 可编辑文案必须保留原有 `data-k` 标识；同一标识的文案修改应同步更新，并兼容 localStorage 保存、导出 HTML 和恢复默认功能。
- 需求说明面板本身不得被左侧抽屉、图片查看器、遮罩层或编辑工具覆盖。

## 12. 原型缩放与尺寸适配规则

优先通过内部布局适配原型，不要直接把整个原型缩小到难以阅读：

- 第一优先级：调整原型内部容器宽度、表格滚动、栅格列数、内边距和浏览器外框尺寸，使内容自然适配左侧面板。
- 第二优先级：只有内部布局仍无法适配时，才使用整体缩放；缩放必须设置 `transform-origin: top left`。
- 使用缩放时，根据父容器可用宽度动态计算比例，保证点击区域和视觉位置一致；不要通过极度缩小字体或控件解决布局问题。
- 缩放后的原型必须保持文字可读，顶部栏、侧边菜单、查询区、表格和分页仍应可辨识。
- 抽屉、遮罩和图片查看器不得因缩放出现尺寸错位、偏移、超出浏览器窗口或覆盖右侧说明。
- 需要缩放时，优先缩放浏览器内容容器，不要缩放右侧需求说明、编辑工具或外层页面。
- 如果使用固定设计宽度，父容器必须允许内部横向滚动；不能通过裁切隐藏关键字段和操作。
- 交付前至少检查 1440×900、1680×1050 和 1920×1080 三种桌面尺寸；重点检查文字清晰度、点击位置、独立滚动、表格横向滚动和抽屉边界。
- 不引入第三方缩放框架或外部 CDN；使用原生 CSS 和 JavaScript 完成尺寸适配。

## 13. 默认登录用户信息规范

- 所有后台原型右上角默认展示用户名称“Flora”。
- 优先使用用户提供的头像。
- 单文件 HTML 中头像必须转换为 Base64 Data URL 内嵌。
- 未提供头像时，使用带“F”字母的圆形占位头像。
- 不得生成随机中文姓名。
- 不得使用案例中的开发者、创建人或业务人员姓名作为登录用户。
- 用户信息仅用于原型展示，不代表业务权限角色。

## 14. 终端规则分流

- Web 原型读取本文件，APP/H5 原型读取 `references/app-prototype-rules.md`。
- Web 与 APP 同时存在时，分别读取对应规则并生成独立原型文件。
- 两种原型都使用左侧约 65% 原型、右侧约 35% 需求说明的外层布局，并保持原型与需求说明同步。
- Web 原型使用浏览器窗口式容器；APP/H5 原型使用手机设备外壳式容器。
- 不允许混用两类页面结构：APP/H5 不直接套用 Web 后台宽表格，Web 也不通过缩小手机页面替代后台布局。
